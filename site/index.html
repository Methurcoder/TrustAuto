sudo を打たなくていい。ただし、許可した範囲だけ。

TrustAuto は Linux 向けの自動権限昇格ツールです。普段どおりにコマンドを打つだけで、管理者がポリシーで許可した操作は root で動きます。既定では、未知のコマンドや高リスクの操作は、承認を求めるか拒否します。

ダウンロード GitHub

bash / zsh
journalctl -u nginx --no-pager ルールで許可。パスワードなしで実行 root
apt search vim 権限が要らない。ユーザー権限のまま実行 user
apt install ./evil.deb 型付きルールに合わない。管理者の承認を要求 承認
trustauto run -- mkfs -t ext4 /dev/sda 拒否ルールに一致。実行しない 拒否

既定では、どのルールにも合わなければ自動で昇格しません

判定は 5 種類のルールで決まります。複数に一致したら厳しいほうを採用し、ファイルに書いた順番には左右されません。

  1. 0 0> <拒否deny

    どのモードでも実行しません。

  2. 0 0? ?承認ask

    常に承認を求めます。

  3. 0 0^ ^rootallow

    その場で昇格します。既定の hybrid では、ML がリスクが高いと判定したら承認を求めます。

  4. 0 0? ?承認envelope

    範囲だけを決めておきます。既定の hybrid では、ML がリスクが低いと判定したときだけ昇格し、それ以外は承認を求めます。

  5. 0 00 0useruser

    権限を上げずに実行します。

先に並んでいるルールほど優先されます

オプションの注入を、型で防ぎます

拒否リストは完全にできません。apt-get -o ... や find -exec のように、普通のコマンドから root シェルに抜ける道があるからです。

そこで、許可するコマンドと引数の形をポリシーに書きます。{pkg} や {unit} は - で始まる値に一致しないので、オプションを紛れ込ませることはできません。

# /etc/trustauto/policy.toml
[[rule]]
id = "journal-unit"
action = "allow"
bin = "/usr/bin/journalctl"
args = ["-u", "{unit}", "--no-pager"]

[[rule]]
id = "no-mkfs"
action = "deny"
bin = "/usr/sbin/mkfs"
args = ["{any}*"]

常駐せず、コマンドを打った瞬間だけ動きます

root で動くコードは小さなブローカーに分けてあります。シェル側の判定を信用せず、自分で判定し直してから、実行するコマンドに置き換わります。

シェル関数 → trustauto （権限なし）
              ├─ user の判定 → ユーザー権限でそのまま実行
              └─ trustauto-broker（setuid root）
                   ├ 判定をやり直す
                   ├ 監査ログを書く （失敗したら昇格しない）
                   ├ 必要なら PAM で承認を取る
                   └ 実行するコマンドに置き換わる
0 MB
アイドル時の追加メモリ。常駐プロセスはありません。
0.2 µs
ルールだけで決まる判定の時間（p99、Linux VM）。ML を使う判定は約 7 ms で、前もって作った機械の情報の索引の読み込みに約 26 ms かかります。プロセスの起動とポリシーの解析は含みません。
監査ログ
昇格、承認、拒否の判定と理由を記録します。ログを書けなければ昇格しません。権限を上げない user の判定は記録しません。

何が起きるかは、実行する前に確かめられます

普段はいつもどおりに打つだけです。判定の理由を見たいときや、一時的に止めたいときに次のコマンドを使います。

trustauto explain -- apt install htop実行せずに、判定と理由だけを表示します。
trustauto history 20判定の履歴を表示します。承認者は全員分、それ以外は自分の分だけ見られます。
trustauto off / on自分の自動昇格を切り替えます。開いているシェルにもすぐ反映されます。
trustauto settingオンかオフか、今のモード、モデルと機械の情報の状態、外部通信の確認を表示します。
trustauto checkポリシーの書き方を検証します。

導入

今はソースからビルドします。Debian と Ubuntu を想定した手順です。

  1. ダウンロードしてインストールする

    git clone https://github.com/Methurcoder/TrustAuto.git
cd TrustAuto
sudo apt install build-essential libpam0g-dev cargo
cargo build --release
sudo scripts/install.sh

    ビルドを待つあいだに、GitHub でスターを押してもらえると励みになります。

  2. ポリシーを設定する

    /etc/trustauto/policy.toml を編集し、approval.approvers に承認者を書きます。空のままだと、承認が必要な操作はすべて拒否されます。

    trustauto check

  3. 使うユーザーをグループに入れる

    sudo usermod -aG trustauto ユーザー名

    入れたあと、ログインし直します。グループに入れることは、ポリシーの許可範囲をそのユーザーに渡すことと同じです。

  4. シェルに読み込ませる

    ~/.bashrc に追加します。zsh なら ~/.zshrc に、bash を zsh に変えて追加します。

    eval "$(trustauto shell-init bash)"

入れる前に知っておいてください

root に関わるツールなので、できないことも先に書いておきます。

  • 許可した範囲は、そのユーザーの全プログラムにも開かれます

    パスワードなしで昇格できるので、人とマルウェアを区別できません。allow には、そのユーザーの権限で動くマルウェアに実行されても許容できる操作だけを入れてください。端末を要求する設定で多くのバックグラウンド実行は止まりますが、疑似端末を使うものは止まりません。

  • 外部と通信するコマンドは、毎回承認を求めます

    apt update、apt install、curl、git pull、URL を含むものなどは、allow ルールがあっても、どのモードでも承認が必要です。不要なら policy.toml の [network] で ask = false にします。

  • 外部の監査は受けていません

    v1.0.0-preview.1 の統合テストは、Ubuntu 26.04（arm64）の VM 1 環境で 175 件すべて合格です。普段使いのマシンに入れる前に、内容を確認してください。

  • 終了コードは記録しません

    実行するコマンドに置き換わるので、履歴に残るのは開始までです。

  • 常に / で実行します

    昇格したコマンドでは、相対パスの引数は動きません。

  • 承認は要求元の端末で行います

    別の端末にいる承認者には対応していません。

ML モード（研究中）

既定の hybrid は、ルールで決めた範囲の中だけ ML のリスク判定を使います。ML がどう判定しても、allow と envelope の外にあるコマンドは自動では昇格しません。ルールの外まで ML に任せる ml は、プレビューとして選べます。

ruleルールだけで判定します。allow はその場で昇格し、envelope は承認を求めます。
hybrid（既定）ルールと ML で判定します。allow はリスクが高いと判定しない限り昇格し、envelope はリスクが低いと判定したときだけ昇格します。
ml（プレビュー、高リスク）ML だけで判定します。root が必要なコマンドは、ルールがなくても、リスクが低いと判定すれば昇格します。

モデルはまだ合格基準を満たしていません。開発用の 4 台で測ったところ、未見の機械で危険な操作の見逃しが 217 グループ中 8 件（95% 上限 6.6%）、無害な操作の自動許可が 71.2% でした。独立した機械での最終テストはまだです。

どのモードでも deny と ask が先に効きます。ml でも、シェル、インタープリター、カーネルやディスクを操作するツールは必ず承認を求め、学習例が少ないプログラムも既定では承認を求めます。

ML は trustauto-facts が集める機械の情報を使います。情報がない、または 8 日より古いと、ML を通る判定はすべて承認待ちになり、既定の hybrid では allow のコマンドも承認を求めます。モードは sudo trustauto mode rule|hybrid|ml で変え、今の状態は trustauto setting で確かめられます。
