# ルールの外も ML が判断するモードの計画

状態: 4 台で比較まで実施し、目標は未達です（結果は [ML_EXPERIMENT_5.md](ML_EXPERIMENT_5.md)）。v1.0.0-preview.1 で、round 4 の `known_avg_facts_transformer` を `ml` モード（ML のみ、プレビュー）として組み込みました（2026-11-06、ユーザー判断）。このモードを選んだときだけ、ML の誤判定で範囲外の root 権限を与えうるので、管理者が `sudo trustauto mode ml` で明示的に選び、学習にないプログラムを判定させるかを別に確認します。`rule` と `hybrid` の「ML の誤判定だけで無制限の root 権限を与えない」は変えていません。

## 流れ

1. **コマンド収集:** `ml/truth/collect_commands.py` が NL2Bash、tldr-pages、GTFOBins、Atomic Red Team、permission-command-corpus からコマンドを集めます。危険かどうかで絞らず、攻撃の手順も入れます。
2. **機械に合わせる:** `ml/truth/action_cases.py` が、存在しないパスや `username`、`#{file}` のような未置換の文字を、その機械に実在するものへ置き換えます。これとは別に、機械の実物からランダムに選んだ操作も入れます。
3. **隔離して実行:** `ml/truth/action_lab.py` がコマンドを使い捨てのコンテナで実行します。
4. **機械的な検査:** 壊れたか、権限面で何が変わったか、実行中の状態（サービス、ネットワーク、ホスト名、`sysctl`）が変わったかを記録します。ラベルは `ml/truth/label_actions.py` が決めます。
5. **教師 AI:** 検査で決まらず、かつ簡単なものだけを Gemini に見てもらいます。
6. **学習と比較:** 実行前に取れる情報だけで学習し、下の 3 つのモデルを比べます。
7. **最終テスト:** 開発で基準に近づいたら方法を固定し、新しい機械で 1 回だけ測ります。

## 環境

開発は Ubuntu 26.10（`ubu2610`）と Debian 13.7（`deb137`）で行います。Web や DB などの役割は既存の機械と変えています。

2 台だけでは「未知の環境」を十分に測れず、1 台の独立した危険グループが足りない場合もあります。足りなければ、同じ OS で役割の違う機械を足します。最終テストの機械は、方法を固定してから作ります。

## 外に送らないための対策

| 対策 | 内容 |
|---|---|
| コンテナ | ネットワークはループバックだけ。開始時に確かめ、外への経路があれば止まる |
| 実行の方法 | `systemd-run` でコンテナの権限制限と seccomp の中で実行する。`nsenter` は VM の権限を引き継ぐので使わない |
| VM | コーパスの実行中は `lab_firewall.sh` で外への通信をすべて遮断し、遮断を確かめてから始める |
| host ネットワーク | `apt` の固定の操作だけが使う。コーパスのコマンドは使えない |
| 秘密情報 | コンテナにあるのはダミーだけで、本物の認証情報は置かない。VM 以外では実行しない |

## 実行しないコマンド

コマンドのファイルには理由と一緒に残しますが、実行はしません。実際の判定では ML に任せず、承認待ちにします。

- **中身が見えないもの:** シェル、インタープリター、ビルドツール、リモート接続、`./x` など。
- **コンテナで確かめられないもの:** `mkfs`、`fstrim`、`mount`、`modprobe`、ブートローダー、ブロックデバイス、カーネルの設定など。

## ラベルの決め方

| 結果 | 決め方 |
|---|---|
| 危険（確定） | 確認項目が壊れた、setuid やケーパビリティの追加、UID 0、`sudoers`、`authorized_keys`、PAM、`ld.so.preload`、誰でも書ける変更、新しいポート、ダミーの秘密の漏えい、非公開ファイルの読み出し、シェルやインタープリターの起動 |
| 無害（確定） | 検査で何も変わらず、上のどれにも当たらない |
| 教師 AI へ | 検査では決まらず、変更が小さいもの（ファイル 5 個以下）、実行中の状態だけが変わったもの、またはパッケージのインストール |
| REVIEW | それ以外の複雑なもの、実行が失敗して結果がわからないもの |

- GTFOBins の中には、端末がないと動作せず何も起きないものがあります。無害と決めつけず、シェルの起動を確認できないものは REVIEW にします。
- コマンドがなくて失敗した行は、学習に使いません。
- 必ず検出されるはずの 15 件（`known_bad`）を 1 件でも見逃したら、ラボの不具合なので止めます。

## 教師 AI（Gemini）

**ALLOW の範囲（2026-11-04 決定）:** 普段なら本人が `sudo` を打つ操作で、間違いでも簡単に戻せて、ほかに影響せず、誰の権限も増やさないなら許可します。最初の「一般ユーザーが承認なしで実行してよいか」という聞き方では、変更を伴う操作をほぼすべて拒否し、50 行中 48 行が「何も変わっていなければ許可」という単純なルールと同じ答えでした。

精度を保証できないので、次の範囲に限ります。

- 判定を変えられるのは「検査で決まらなかった簡単なもの」だけで、確定した結果は変えられません。
- 確定済みの行を混ぜて答えさせ、Gemini の精度を測ります。
- **汚染対策（2026-11-04 追加）:** 各バッチに既知の危険例を 2 行ずつ混ぜます。使うのはどの機械でも害になるコマンド（`known_bad`、パスワードの削除、`sudoers` への `NOPASSWD` の追記、`authorized_keys` への鍵の追記）だけで、検査の失敗で危険になった行はラボの判定が厳しい疑いがあるので使いません。1 行でも ALLOW と答えるか答えを省いたバッチは、ラベルに使わず REVIEW にします。合格するまで聞き直すと都合のよい答えだけが残るので、再送しません。ただし精度の測定には含めます。全バッチの 10% を超えて捨てたら、全体を使いません。
- **`deb137` の結果（2026-11-04）:** 654 行すべてに回答があり、14 バッチ中 1 つを捨てました。ただし捨てた原因は `ld.so.preload` への空行の追記で、Gemini の判断が正しく、危険例の選び方の誤りでした。後から救うと基準を緩めることになるので捨てたままにし、`ubu2610` から危険例を上の範囲に絞ります。`deb137` の答えは旧版の並びなので、今のコードでは読み直せません（結果は保存済み）。
- **起動時に効く変更は REVIEW（2026-11-04）:** `etc/systemd/system/` を変える行は、Gemini の答えによらず REVIEW にします。Gemini は `systemd-udevd`、`systemd-remount-fs`、`kmod` の `mask` も許可しましたが、コンテナでも送るデータでも実機の起動への影響は分かりません。
- **基準 1 の変更（2026-11-04 ユーザー承認）:** 確定した危険な行に ALLOW が出ないことを送信の条件にしていましたが、外しました。代わりに、学習に使う前に、ALLOW が正しい場所に出ているかを確かめます。確定した危険な行で ALLOW と答えたものを 1 行ずつ読み、教師行の ALLOW を操作の種類ごとに確かめます。
- **`ubu2610` の結果（2026-11-05）:** 636 行すべてに回答があり、捨てたバッチはありません。混ぜた危険例 26 行はすべて DENY でした。確定した危険な行で ALLOW になった 3 行（`routel`、`chmod 644 /etc/security/capability.conf`、`sudoers.d` へのコメントの追記）は、どれもラボの判定が厳しい疑いがあります。ただし実機では確かめていません。バッチ 8 は `agy` のエラーで答えが返らなかったので、そのバッチだけ送り直しました。答えを読んでいないので、都合のよい答えを選ぶことにはなりません。
- **何も起きなかっただけの行は無害にしない（2026-11-05）:** 変更を目的とするコマンドが、今回は何も変えなかった行を、モデルを比べる前に REVIEW に移しました。例: 空の入力の `chpasswd`、`pkill -9 -x sshd`、ファイルがない状態の `rm -f /etc/machine-id`、既に起動中のサービスへの `systemctl start`、更新対象がない `apt-get autoremove`。`deb137` で 168 行、`ubu2610` で 179 行が動きました。対象のプログラムと操作は、両方の機械の行を読んで `train_actions.py` に手で並べたものなので、漏れがありえます。
- 送るのはコマンド、入力、終了コード、対象の権限、変更されたパス、変わった実行中の状態の種類だけです。ダミーの秘密は取り除きます。
- どの行が測定用かと、検査の結果は Gemini に見せません。見せると精度の測定が甘くなるためです。
- コマンドやパスの文字列はデータとして渡します。Antigravity CLI（`agy`）を空のフォルダで、すべてのツールを拒否する設定で実行します。ただし `search_web` だけはこの設定で止まりません。ツールを使おうとした回と、Thinking がなかった回の答えは捨てます。
- シェルなど別のプログラムを起動できるコマンドは、今回の実行で何も起きなくても DENY と答えるよう指示します。
- Gemini が見るのは実行結果の一部だけなので、検査の失敗でしか分からない被害（例: `systemd-tmpfiles --create --boot` でログインできなくなる）は見抜けません。検査で危険と確定した行を Gemini の答えで変えないのは、このためです。
- Mac から送ります。`TrustAuto-Lab` からは送りません。

## 評価

- 誤承認率は、機械的に確定した危険な行で測ります。教師 AI が決めた分は、別の数字として出します。教師 AI との一致率は、安全性の証明として使いません。
- 3 分類（ALLOW / DENY / REVIEW）は残しますが、合否は ALLOW かそれ以外かで測ります。
- 無害な操作の自動許可は、何も変わらなかった行と、変更を伴う行（教師 AI が許可した行）を分けて出します。検査で無害と確定する行はすべて何も変わらない行なので、合わせた数字だけでは、読むだけのコマンドを許可しているのか区別できません。
- 分割は、機械、対象のパッケージやパス、操作の種類の 3 つです。学習にない種類の操作での結果を必ず出します。
- 比べるモデル:
  1. 構文で切った特徴と機械の事実を使う決定木
  2. 同じ入力を使う小さな Transformer
  3. 文字列だけの Transformer
- 難しい事例の追加学習は、開発用の機械だけで行います。

## わかっている限界

- コンテナではカーネル、ブート、実デバイスの影響を確かめられません。
- 悪意のある相手に対しては、1.8% 未満を保証できません（基準は 2026-11-05 に 1% 未満から変更）。今回は誤操作を主な対象として測ります。
- `nft flush ruleset` はルールのない機械では何も変えないので、無害と記録されます。ラベルはその機械での結果で、別の機械でも安全という意味ではありません。
- 実行時の判定は 10 ms に収まるか未測定です。ファイルの使われ方は事前の計算と、更新の仕組みが必要です。
