# ML 実験 4: 複数の機械で、未見の機械とパッケージを測る

**結論: 不合格です。7 台で、危険な操作の自動許可は 14/234 グループ（95% 上限 9.2%）でした。目標の 1% 未満に届いていないので、モデルは組み込みません。**

無害な操作の自動許可は全体で 70.7% ですが、`remove` だけなら 49.3% です。`stop` と `restart` に支えられた数字です。

最終テストは行っていません。ここの数字はすべて開発データのもので、方法を調整しながら見ているので、実際より良く出ている可能性があります。

## 方法

`ml/truth/build_profile.sh` で、OS と役割の違うサーバーを 7 台作りました。

| 名前 | OS | ケース数 | 備考 |
|---|---|---|---|
| `deb13` | Debian 13 | 518 | |
| `ubu24` | Ubuntu 24.04 | 588 | |
| `deb12` | Debian 12 | 447 | |
| `ubu22` | Ubuntu 22.04 | 562 | |
| `deb11` | Debian 11 | 475 | 起動しない行が 72 件 |
| `deb14` | Debian 14 | 563 | 変更前から `sudo`、`role_dns`、`role_smb` が失敗する |
| `ubu20` | Ubuntu 20.04 | 503 | |

1 ケースごとに使い捨てのコンテナを作り、`apt remove`、`systemctl stop`、`systemctl restart` を実行して、確認項目を調べました。Web や DB などの役割は、ポートが開いているかではなく、プロトコルで応答するかを確かめています。

- **危険の定義:** 変更前に合格していた確認項目が、実行後に失敗すること。依頼どおりに DB を止めた場合も含みます。
- **独立性:** 同じソースパッケージのケースは、機械が違っても 1 グループとして数えます。
- **評価:** 各行を、その機械を学習に使っていないモデルで採点します。パッケージも、次の例外を除いて学習から外します。全機械に共通する 45 グループと `systemd` は、基本システムの学習に必要なので、常に学習に残します。この分の結果は別に出しています。
- **閾値:** 学習データの中だけで決めます。危険な行のうち、自動許可される割合が 1% 以下になる値です。
- **合格:** 危険の自動許可の 95% 上限（グループ単位）が 1% 未満で、無害の自動許可が 70% 以上。

失敗した行は、もう一度実行して確かめました。`deb11`、`deb14`、`ubu20` の 681 件はすべて 1 回目と同じ結果でした。負荷による揺れではありません。

## 結果

`ml/truth/train_usage.py` の結果です。全 3,233 行のうち、危険は 1,071 行、判定不能は 91 行です。判定不能の行も危険として数えています。

| 対象 | 危険の自動許可（グループ） | 95% 上限 | 無害の自動許可 |
|---|---|---|---|
| **全体** | **14/234** | **9.2%** | **70.7%** |
| `remove` | 11/232 | 7.7% | 49.3% |
| `stop` / `restart` | 3/24 | 29.2% | 79.8% |
| 学習から外したパッケージ | 9/198 | 7.8% | 52.4% |
| 常に学習に残したパッケージ | 5/36 | 27.0% | 79.3% |

## 機械を増やしても良くならなかった

同じ 4 台をテストにして、学習に使う機械だけを変えました。危険の見逃しを 1% に揃えたときの、無害の自動許可です。

| 追加した機械 | 全体 | `remove` |
|---|---|---|
| なし | 62.0% | 27.6% |
| `deb11` | 63.8% | 34.7% |
| `deb14` | 47.3% | 21.1% |
| 両方 | 49.7% | 26.6% |

この比較は `ubu20` を直す前に行ったものです。今回の方法では、機械を足すだけでは 1% に近づかないと考えられます。

## 見逃したもの

- **確認項目が 1 つだけ:** `net_config`（`netplan` 関連）、`role_imap`、`role_cups` などです。
- **機械を止めるもの:** `deb14` の `restart systemd-sysinstall`、`restart initrd-parse-etc`、`restart systemd-factory-reset-reboot` です。`deb14` は新しい OS で、学習に同じ種類のユニットがありません。ここが最も危険な見逃しです。
- **判定不能:** `remove sudo` と `remove diffutils` は全機械で失敗して判定できず、学習から外れていますが、テストでは危険として数えています。

## 実験中に見つけた問題

| 問題 | 影響 | 対応 |
|---|---|---|
| `ubu20` で古い `dpkg` が使う `/var/lib/dpkg/available` がなかった | `remove` が 293 件すべて失敗し、その結果を含む 7 台の数字（63/272）は無効になった | イメージを直して再実行した |
| 閾値を行の数で決めている | パッケージの多いグループに引っ張られる。`deb11` を足すと閾値が 0.002〜0.018 から 0.03〜0.09 へ緩んだ | 未対応。変更するなら 1 回の試行として数える |

## 数字の限界

1. **開発データの数字です。** 特徴量と制約を結果を見て選んだので、実際より良く出ている可能性があります。
2. **コンテナの中で測っています。** カーネル、ブート、実デバイスへの影響は見えません。実機の再起動での確認はしていません。
3. **対象は 3 種類の操作だけです。** `remove`、`stop`、`restart` の外は、この実験では何も言えません。ルールの外を扱うモードは [別の計画](ML_OUTSIDE_RULES_PLAN.md) で進めます。
4. **権限の変化は見ていません。** この実験の危険は「壊れた」だけです。
5. **悪意のある相手は対象外です。** 主に誤操作を測っています。
6. **10 ms の目標は未測定です。** 特徴量には `apt` の実行計画と、ファイルの使われ方の走査が必要です。
7. **製品には組み込めません。** このモデルは機械の事実を使うので、製品の文字列モデルとは別物です。

## 再現手順

スクリプトは `ml/truth/` にあります。データの収集は、使い捨ての Linux VM で root として実行します。

```bash
sudo TRUSTAUTO_TRUTH_DISPOSABLE=yes TRUSTAUTO_TRUTH_PROFILE=NAME python3 ml/truth/truth_lab.py batch CASES OUT --workers 3
```

```bash
python3 ml/truth/train_usage.py DATA_DIR deb13 ubu24 deb12 ubu22 deb11 deb14 ubu20
```
