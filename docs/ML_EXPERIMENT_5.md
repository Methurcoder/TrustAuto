# 実験 5: ルールの外も ML が判断するモードの比較

実施: 2026-11-05。計画は [ML_OUTSIDE_RULES_PLAN.md](ML_OUTSIDE_RULES_PLAN.md)。再現は `ml/truth/train_actions.py` で、ラベル、結果、Gemini の回答、機械の事実は `ml/truth/experiment_5/` にあります（`train_actions.py experiment_5/data experiment_5 MODEL SPLIT deb137 ubu2610`）。

## 結論

**目標は未達です。** 32 通りすべて不合格で、モデルは本体に組み込んでいません。

- 無害な操作の自動許可は最大 27.8% で、目標の 70% に遠く届きません。
- 危険な操作の自動許可は、95% 上限で 1% 未満になった組み合わせがありません。今の 161 グループでは、0 件見逃しでも上限が 1.8% なので、データ量の面でも 1% 未満を示せません。
- 学習にない種類の操作は、ほぼ見分けられません（AUC 0.47〜0.62）。
- プログラムごとの行数の少なさは、制約の一部です。未見の機械では無害な行の 36%（447/1,258）が行数不足で判定に進めません。ただし、判定に進めた行でも多くは通らず、行数が増えるほど通りやすいという傾向も見えません。

### ALLOW の場所の確認

「正しい場所で ALLOW が出ているか」は次の範囲で読みました。ALLOW の判断が正しいかを実機で確かめたわけではありません。

- `ubu2610` の確定した危険な行の ALLOW は 3 行で、どれもラボの判定が厳しい疑いがあります（`routel`、`chmod 644 /etc/security/capability.conf`、`sudoers.d` へのコメントの追記）。
- `deb137` の 6 行のうち、`systemd-tmpfiles --create --boot` は Gemini の見逃しです。残り 5 行はラボの判定が厳しい疑いがあります。
- 教師行の ALLOW は操作の種類ごとに読みました。件数の多い種類は一部の見本だけです。

### モデルを比べる前に直したラベル

変更を目的とするコマンドが今回は何も変えなかった行を、REVIEW に移しました。`chpasswd`（空の入力）、`pkill -9 -x sshd`、ファイルがない状態の `rm -f /etc/machine-id`、起動中のサービスへの `systemctl start` などです。`deb137` で 168 行、`ubu2610` で 179 行が動きました。

対象のプログラムと操作は、行を読んで手で並べたものなので、漏れがありえます。この変更で無害の母数が減るため、無害の割合はこの変更の前と比べられません。

## 結果

- 分割の「機械」は、もう一方の機械だけで学習してテストします。「対象」は、学習にないパッケージやパスです。「操作」は、学習にないプログラムです。
- 危険はグループ単位で、「見逃し / 全体」と 95% 上限です。無害は Gemini が許可した行も含みます。
- しきい値は、学習側の交差検証で確定した危険な行の 1% を通す値です。

| モデル | 機械: 危険 | 機械: 無害 | 対象: 危険 | 対象: 無害 | 操作: 危険 | 操作: 無害 |
|---|---|---|---|---|---|---|
| 決定木 | 0/161（1.8%） | 0.0% | 0/161（1.8%） | 0.0% | 0/161（1.8%） | 0.0% |
| ブースティング | 1/161（2.9%） | 7.7% | 7/161（8.0%） | 10.8% | 5/161（6.4%） | 2.8% |
| Transformer（構文と機械の事実） | 3/161（4.7%） | 16.4% | 10/161（10.3%） | 13.8% | 43/161（33.0%） | 18.2% |
| Transformer（文字列のみ） | 0/161（1.8%） | 6.4% | 11/161（11.1%） | 19.6% | 1/161（2.9%） | 4.3% |

決定木は 1% のしきい値がスコア 0 になり、何も許可しません。ブースティングは比較のために足したもので、最初に決めた 3 モデルには入っていません。

### 2 回目: 学習で許可された行が 3 行未満のプログラムは通さない（16 通り）

1 回目で見逃しの低スコアを調べると、`capsh --` や `mawk BEGIN{system("/bin/sh")}` のように、学習にほとんど行がないプログラムが並びました。そこで、それらを ML に判定させない変種を比べました。

| モデル | 機械: 危険 | 機械: 無害 | 対象: 危険 | 対象: 無害 |
|---|---|---|---|---|
| 決定木 | 0/161（1.8%） | 0.0% | 6/161（7.2%） | 16.8% |
| ブースティング | 2/161（3.9%） | 12.2% | 3/161（4.7%） | 12.6% |
| Transformer（構文と機械の事実） | 1/161（2.9%） | 20.1% | 3/161（4.7%） | 15.1% |
| Transformer（文字列のみ） | 3/161（4.7%） | 27.8% | 7/161（8.0%） | 17.1% |

学習にない操作は、どのモデルも何も許可しません（危険 0/161、無害 0%）。

未見の機械で一番バランスがよいのは、構文と機械の事実を使う Transformer のこの変種です。無害の内訳は、変更なし 161/901（17.9%）、Gemini が許可した変更あり 92/357（25.8%）です。ただし許可された行の多くは `cp` と `cat` で、変更を伴う操作を広く通せているわけではありません。

## 読み取れること

1. **70% は今のデータでは届きません。** 2 回目の方式で ML に判定を任せられる無害な行は、未見の機械で 64.5%、未見の対象で 41.1%、機械と対象の両方が未見で 22.3% までです。モデルを変えても、ここは超えられません。
2. **1% 未満の証明には約 300 グループ要ります。** 今は 161 グループです。1 台で約 100 グループでも、2 台目はパッケージの多くが重なるので、台数に比例しては増えません。
3. **学習にない操作は当てになりません。** 1 回目の構文と機械の事実を使う Transformer は、学習になかった `truncate`、`passwd`、`userdel` を通しました。プログラムの名前に頼って学んでいるので、知らない名前には判断の手がかりがありません。2 回目の方式なら、こうした操作は承認待ちになります。
4. **本物の見逃しがあります。** `cp /etc/ssh/ssh_host_ecdsa_key /tmp/ta-copy` は、構文と機械の事実を使う Transformer とブースティングの 2 回目の未見の機械の結果で通りました。秘密鍵のコピーで、ラボの判定が厳しいせいとは言えません。
5. **REVIEW の行を通している点は、危険の数字に出ません。** 2 回目の構文と機械の事実を使う Transformer は、REVIEW の 49/2,090 行を通しました。`systemctl start debug-shell` のように危険なものも含みます。

## この数字の限界

- 2 台は開発データです。今回の 2 回の試行とラベルの修正を見た後なので、数字は実際より良く出ている可能性があります。最終テストは行っていません。
- ラベルはコンテナでの結果です。カーネル、ブート、実デバイスへの影響は見えません。
- Gemini のラベルは精度を保証できません。安全性は確定した危険な行だけで測っています。
- `deb137` のバッチ 2 は、危険例の選び方の誤りで捨てたままです。そのため `deb137` と `ubu2610` では危険例の範囲が違います。
- 基準 1（確定した危険な行に ALLOW を出さない）は、送信の条件から外しました（2026-11-04 ユーザー承認）。
- 誤操作を主な対象として測っています。悪意のある相手には 1% 未満を保証できません。

## 次の候補

モデルを変えるより、データを増やすのが先です。

1. 今の 2 台で、よく使うプログラムの行を増やします。2 回目の方式で判定を任せられる範囲が広がるかを見ます。
2. 役割の違う機械を足して、独立した危険グループを約 300 まで増やします。
3. それでも基準に近づいたら方法を固定し、新しい機械で 1 回だけ測ります。

## 基準の変更（2026-11-05、ユーザー判断）

危険の基準を 1% 未満から **1.8% 未満**に緩めました。自動許可率を重視するためです。無害 70% 以上は変えていません。

- 95% 上限で判定する方法は変えません。1.8% を満たすには、見逃し 0 件で 165 グループ、1 件で 262 グループ、2 件で 348 グループ必要です。
- 学習側で決めるしきい値も、確定した危険な行の 1.8% を通す値に変えました（`RISKY_BUDGET`）。
- **この変更は、ここまでの結果を見た後の判断です。** 1% の基準で測った表と、1.8% の基準で測った表はしきい値が違うので、直接比べられません。この節より前の表と、下の「追加実験」の表はすべて 1% のしきい値です。

## Gemini 3.8 Flash の試験（2026-11-05）

Argon の枠が残り 1% になり、リセットまで 4 日 18 時間あるため、`gemini-3.8-flash-high` を試しました。Argon が答え済みの 6 バッチ（300 行、新しい行なし）を送って比べました。回答は `experiment_5/flash_try/` にあります。

| 確認 | Flash | Argon（同じ行） |
|---|---|---|
| 混ぜた危険例 | DENY 12/12 | DENY 12/12 |
| 確定した危険な行への ALLOW | 2/18 | 0/18 |
| 確定した無害な行への ALLOW | 42/45 | 41/45 |
| 教師行の ALLOW / DENY / REVIEW | 117 / 107 / 1 | 96 / 124 / 5 |

- 教師行の一致は 190/225（84%）です。同じバッチの再送では 48/50 が同じ答えでした。
- Thinking は毎回出ています。1 バッチ 240〜400 秒で、Argon より遅めです。
- **Flash は甘めです。** 不一致 35 行のうち 24 行は、Argon が DENY で Flash が ALLOW です。多くは `systemctl mask`、`mv /usr/bin/... .bak`、`tee -a` で、`passwd -l mail` も含みます。ALLOW の行が増えると、学習が甘くなり、無害の許可率も良く見えます。

round 4 の教師行は Flash で付け、結果は Flash の行を含む場合と除く場合の両方を出します。6 バッチだけの比較なので、全体の精度を保証するものではありません。

## 追加実験（途中経過、2026-11-05）

ここまでの基準（TrustAuto の危険 95% 上限 1% 未満、無害 70% 以上）に、どの組み合わせも届いていません。

### 外部データセット

`shellkeeper-data`、`cli-command-risk`、`shell-safety-v1.1` を、コマンドを実行せず、文字列としてだけ使いました（`external_rows.py`）。ラベルは他者の方針なので、学習にだけ使い、確定した行として数えず、テストにも使いません。

1 回目のデータだけを使った試験では、未見の機械で最大 26.9%（危険 6/161）で、見逃しは減りませんでした。

### 2 回目の収集と外部データの組み合わせ（未見の機械）

2 回目はよく使うプログラムの行を増やし、両方の機械で 794 件ずつ実行しました。同じコマンドの再収集 117 行を除いて、1 回目に合わせました（`merge_rounds.py`）。Gemini は混ぜた既知の危険例 10 件をすべて拒否し、捨てたバッチはありません。確定した危険な行に出した ALLOW は 2 回目で 7/23、1 回目で 9/125 です。7 件のうち 6 件は、内容がファイルと無関係な `tee -a /etc/cron.d/...` と `tee -a /etc/environment` です。

| モデル | 1 回目のみ 危険 / 無害 | 1+2 回目 危険 / 無害 | 同じ 1 回目の行だけの無害 |
|---|---|---|---|
| known_boost | 2/161 / 12.2% | 2/174 / 21.3% | 23.5% |
| known_facts_transformer | 1/161 / 20.1% | 3/174 / 33.0% | 31.9% |
| known_text_transformer | 3/161 / 27.8% | 2/174 / 32.1% | 30.8% |
| known_ext_boost | 2/161 / 20.0% | 2/174 / 32.3% | 32.7% |
| known_ext_facts_transformer | 4/161 / 23.7% | 6/174 / 45.8% | 45.5% |
| known_ext_text_transformer | 6/161 / 26.9% | 10/174 / 39.2% | 39.0% |

1 回目の行に絞っても無害の許可は増えているので、テストの中身が変わっただけではありません。ただし学習は 1 回ずつで、乱数による揺れは測っていません。危険の見逃しは増えたモデルもあり、基準には届いていません。未見の対象（最大 33.2%、危険 5/174）と、機械と対象の両方が未見（最大 12.9%、危険 9〜11/174）は、まだ大きく足りません。

機械には未見でも、同じコマンドが別の機械の学習に入っています。未見の機械で伸びているのは、その影響を含みます。

### 3 回目の収集（対のデータ）

見逃しの多くは、`cat`、`cp`、`touch`、`mkdir` で秘密のファイルや起動時に読まれる場所を触る行でした。同じプログラムで安全な対象と危険な対象を対にした 750 件（`action_cases.py --pairs`）を両方の機械で収集しました。**この行は見逃しを見てから設計したので、開発の機械の数字はその分だけ良く出ます。**

ラベルの厳しさが疑われる行（`apt-get update` の `started:sh` など）も、見逃しを見た後でラベルを緩めると基準をごまかすことになるので、そのまま数えています。

Gemini は混ぜた危険例 16 件をすべて拒否し、捨てたバッチはありません。ただし教師行 255 行はすべて ALLOW で、ラベルとしての情報はほとんどありません。確定した危険な行への ALLOW は `deb137` で 7/22、`ubu2610` で 12/22 で、多くは起動時に読まれるディレクトリに空のファイルを作る行です。この行のラベルは危険のままです。

3 回分を合わせると `deb137` 3,261 行、`ubu2610` 3,306 行、危険は 192 グループです。

対のデータだけを足すと、構文と機械の事実を使う Transformer の見逃しは 11/192 に増えました（無害 51.7%）。中身の多くは秘密の DB ファイルで、`/var/lib/mysql` という場所の語を覚え、もう一方の機械の `/var/lib/postgresql` を通していました。

### 特徴量の追加

対象が他のユーザーから読めないこと（`target_private`）と、親ディレクトリの事実（`d_*`）を足しました。場所の語を落とす変種（`general_`）も足しました。

**`target_private` は、手で書いたラベル `read_private` をほぼそのまま言い直しています。** 秘密の行の見逃しが調べたモデルで 0/129 になったのは、モデルが定義を学んだだけです。独立した検証にはなりません。

### 乱数を変えた再確認（未見の機械、見逃し / 無害）

同じデータと同じ設定で、乱数だけを 4 通りに変えました。

### 乱数ごとの一致（`experiment_5/seeds/vote.py`）

既存のスコアだけを使い、4 つの乱数がすべて許可した行だけを通した場合です。しきい値はそれぞれの学習側で決めたものなので、テストの行は見ていません。ただし「一致で見る」という案は、上の結果を見てから決めました。

| モデル | 機械: 危険 / 無害 | 対象: 危険 / 無害 |
|---|---|---|
| Transformer（構文と機械の事実） | 0/192（1.5%） / 29.2% | 2/192（3.2%） / 24.8% |
| 同上 + 外部データ | 0/192（1.5%） / 15.6% | 3/192（4.0%） / 29.9% |
| 同上 + 外部データ、場所の語を除去 | 0/192（1.5%） / 19.2% | 3/192（4.0%） / 29.8% |
| 上の 3 種の 12 個すべて | 0/192（1.5%） / 2.8% | 1/192（2.4%） / 17.7% |

見逃しの多くは乱数ごとに違う行で、一致を求めると消えます。その分だけ無害の許可も大きく下がります。

### テストの行を見た上限（`experiment_5/seeds/curve.py`）

スコアを平均し、しきい値をテストの行から逆算した診断です。**実際には使えない上限です。**

| 平均するもの | 機械: 見逃し 0 | 見逃し 1 | 見逃し 2 | 見逃し 4 |
|---|---|---|---|---|
| Transformer（構文と機械の事実）の 4 乱数 | 34.9% | 43.0% | 57.4% | 67.2% |
| 3 種の 12 個 | 31.8% | 60.2% | 63.7% | 65.6% |

しきい値を完璧に当てても、見逃し 4 グループで 70% に届きません。今のデータと特徴量では、しきい値の工夫だけでは目標に届かないことを示します。

### 1.8% の基準での比較（`experiment_5/m6_budget_1_8/`、すべて不合格）

学習側で危険の許容量を 1.8% にして決めたしきい値です。データは 1〜3 回目の収集で、危険は 192 グループです。`known_avg_*` は 4 つの乱数のスコアの平均で、しきい値も平均のスコアで決めました。しきい値を決めるときにテストの行は見ていませんが、平均するという案は上の 2 つの表を見てから決めました。

| モデル | 機械: 危険（95% 上限） / 無害 | 対象: 危険（95% 上限） / 無害 |
|---|---|---|
| 4 乱数の平均（構文と機械の事実） | 4/192（4.7%） / 62.9% | 6/192（6.1%） / 45.3% |
| 同上 + 外部データ | 3/192（4.0%） / 62.6% | 8/192（7.4%） / 48.7% |
| 同上 + 外部データ、場所の語を除去 | 4/192（4.7%） / 61.4% | 9/192（8.0%） / 47.8% |
| 勾配ブースティング | 5/192（5.4%） / 45.6% | 6/192（6.1%） / 38.1% |
| 勾配ブースティング + 外部データ | 11/192（9.3%） / 62.6% | 8/192（7.4%） / 43.4% |

- 基準の 95% 上限 1.8% 未満と無害 70% 以上の両方を満たすものはありません。

### 4 回目の収集で見つかったラボの不具合（2026-11-05）

`ubu24` と `deb14` の 1 回目の結果は、どちらも学習に使いません。Gemini にも送っていません。`label_actions.py` の `known_bad` と `control` の検査で見つかりました。行数だけの確認では見つかりませんでした。

| 機械 | 起きたこと | 影響 | 修正 |
|---|---|---|---|
| `ubu24` | コンテナの停止に約 31 秒かかり、待ち時間の 15 秒を超えた | 888 行のうち 449 行が `container did not go away` のエラー。再起動して確かめる行、つまり何かを変えた行が失敗するので、残りは変更のない行に偏る。`known_bad` も検出できない | 下の 2 つの修正 |
| `ubu24` | `systemctl reboot` のコンテナが同じ名前で起動し直し、約 3 時間残って CPU を 1 コア使い続けた | 上と同じ 1 行。残ったコンテナにネットワークはなく、外への影響はない | `stop` で必ず `machinectl terminate` を呼ぶようにした |
| `deb14` | `dnsmasq` が `systemd-resolved` に問い合わせ、それがまた `dnsmasq` に戻るループ。外の DNS がないコンテナでだけ起きる | ランダムな UDP ポートが「新しいポート」に見え、259 行すべてが危険になった。`control` も危険。1 行に約 90 秒かかった | 機械のイメージに `/etc/dnsmasq.d/ta-lab-no-loop.conf`（`no-resolv`）を足した |

- **最初の修正では直りませんでした。** 待ち時間だけを 60 秒に延ばして既知の答えを試すと、`known_bad` 15 行がすべて危険になり、検査に合格しました。しかし 12 行は `check:boot`、つまり再起動できなかったことが理由に含まれていました。`nspawn` を 10 秒で強制終了すると、片付けられなかったマウントが残り、次の起動が拒否されます。そのまま収集すると、変更のある行がすべて誤って危険になるところでした。
- **直したこと:** `truth_lab.py` の `stop` は `nspawn` の終了を 90 秒まで待ちます。`action_lab.py` の `wait_until_gone` は 60 秒にしました。`label_actions.py` は、`known_bad` に `check:boot` が含まれたらラボの不具合として止めます。この検査は 1〜3 回目のすべてのラベルで誤報 0 件で、上の 12 行は検出します。
- **取り直し:** VM の `act4/run2.sh` は、機械ごとに既知の答えを先に実行して検査し、間違っていれば本番を始めずに止めます。終わった後も全行で同じ検査をします。`ubu24` はエラーの行だけ、`deb14` は全行を取り直します。`ubu24` の正常だった 439 行は再起動していない行なので、この不具合の影響を受けません。
- 1〜3 回目の出力に同じエラーはありません（`deb137` と `ubu2610` のすべての出力で 0 行）。再起動した 1,850 行のうち、2 回目の起動ができなかった行は 7 行で、`rm -rf /usr/bin` のような行が多いものの、`ifdown --all` と `systemctl enable systemd-networkd` はこの不具合で誤って危険になった可能性があります。確かめていません。7 行だけなので、結果への影響は小さいと見ています。
- `deb14` のイメージを変えたので、この機械は `dnsmasq` が外へ転送しない構成です。機械の事実（`facts_deb14.json`）はイメージを変える前に取ったものです。
- 1 回目の結果は VM の `~/truth/act4/first_out_ubu24.jsonl` と `dnsloop_out_deb14.jsonl` に残しました。
