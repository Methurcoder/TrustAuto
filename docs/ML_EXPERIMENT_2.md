# ML 実験 2：自作データで学習する

実施日：2026-11-02（macOS）。このモデルは**製品に組み込んでいません**（`ml/model.bin` は空のままです）。

## 結論

ML の順位付けの性能は大きく改善しましたが、ML 単体では合格基準を満たしません。最も良かったのは、リスト検索と ML の併用です。

| 方式（新しいテスト `probe_fresh`） | 危険なコマンドの自動許可 | 定型操作の自動許可 |
|---|---|---|
| ML のみ（しきい値 0.002） | 8/28（28.6%） | 28/36（77.8%） |
| リスト検索のみ | 5/28（17.9%） | 36/36（100%） |
| **リスト + ML** | **2/28（7.1%）** | 28/36（77.8%） |

暫定の合格基準（危険 1% 以下、定型 70% 以上）は、どの方式も満たしていません。

## 実験 1 からの変更

- **データ:** 公開コーパスをやめ、ML が実際に判定するコマンドの形だけを、Ubuntu 26.04 arm64 のメタデータから生成しました（`ml/build_own_dataset.py`）。取得ファイルのハッシュは `ml/data/own/SOURCES.txt` に記録しています。
- **特徴量:** 名前の部品、接頭辞、3 文字組を、操作（`remove`、`stop` など）と組み合わせました。
- **次元:** 2^14 から 2^16 に上げました。モデルは 256 KiB です。

## ラベルの決め方

パッケージは、次のどれかに当てはまれば重要とします。`labels.tsv` に根拠を記録しています。

| 根拠 | 基準 | 該当数（重複あり） |
|---|---|---|
| `essential` | `Essential: yes` | 21 |
| `priority` | `Priority` が `required` か `important` | 223 |
| `minimal` | `ubuntu-minimal` の依存先 | 157 |
| `rdeps` | 300 個以上のパッケージが依存 | 68 |
| `function` | 起動、遠隔接続、ネットワーク、権限、セキュリティ記録に関わる名前（手書きの正規表現） | 334 |

重要パッケージの削除と、重要パッケージのサービスの `stop`、`restart` がラベル 1 です。インストール、`start`、`reload`、ログの閲覧はラベル 0 です。

## 手順

1. 新しいテスト `ml/probe_fresh.tsv`（64 件）を、データ作成の前に書きました。
2. パッケージ単位で 70/15/15 に分割しました。テストの名前は学習に出てきません。テスト問題にある名前も学習から除外しました。
3. 次元、epochs、L2 を検証データだけで比較しました。2^16、epochs 40、L2 1e-5 を採用しました。
4. 検証データでは、危険 1% 以下を満たすしきい値がありませんでした。定型の自動許可が 70% を超えた中で最も厳しい 0.002 に固定しました。
5. テストを開きました。開いた後にラベル、しきい値、モデルは変更していません。

データ作成の途中で 2 点直しましたが、どちらも検証とテストのスコアを見る前です。テスト問題の名前の所有パッケージまで除外していたのをやめたことと、カーネルのパッケージを 40 件に制限したことです。

## 結果（ML のみ）

| テスト | 件数（危険 / 定型） | AUC | 0.002 の危険 | 0.002 の定型 | 0.15 の危険 | 0.15 の定型 |
|---|---|---|---|---|---|---|
| テスト（全形式） | 153 / 4,228 | 0.930 | 12.4% | 82.8% | 39.2% | 97.6% |
| テスト（危険になり得る形式のみ） | 153 / 2,407 | 0.886 | 12.4% | 69.8% | 39.2% | 95.7% |
| `probe_envelope`（実験 1 の AUC は 0.549） | 30 / 32 | 0.949 | 10.0% | 84.4% | 56.7% | 100% |
| `probe_fresh` | 28 / 36 | 0.867 | 28.6% | 77.8% | 67.9% | 100% |

## リスト検索との比較

リスト検索は、ラベルと同じメタデータで名前を引き、未知の名前は定型として扱います。

| テスト | ML のみ | リストのみ | リスト + ML |
|---|---|---|---|
| `probe_envelope` 危険の自動許可 | 3/30 | 2/30 | 0/30 |
| `probe_envelope` 定型の自動許可 | 27/32 | 32/32 | 25/32 |
| `probe_fresh` 危険の自動許可 | 8/28 | 5/28 | 2/28 |
| `probe_fresh` 定型の自動許可 | 28/36 | 36/36 | 28/36 |

併用は、リストと ML の両方が安全と判定したときだけ自動許可します。

リストの見逃しのうち、`systemctl stop cron`（0.000）と `systemctl stop multipathd`（0.001）は ML でも防げませんでした。`cron` は今回のラベル基準（`required`、`important`）に入りません。基準を直すなら、次の実験で新しいテストを作り直す必要があります。

## この結果の限界

- **しきい値が脆い:** 0.002 は極端に低い値で、スコアの較正が取れていません。学習データにある読み取り専用の `dmesg`（0.004）でさえ承認要求になります。SSH 接続などで加わる補正でも容易に判定が変わります。
- **件数が少ない:** テスト問題は 62 件と 64 件です。テストの 153 行も、同じ名前の形式違いを含むので、独立した例はもっと少なくなります。危険なサービスも検証で 3 個、テストで 7 個だけです。
- **`probe_envelope` は甘めに出ている:** 実験 1 で中身を見た後に手書きの正規表現を書いたので、影響を受けています。公平なのは `probe_fresh` の方です。それでも `polkitd` など、同じ人が両方を書いたことによる偏りは残ります。
- **ラベルが機械的:** `php-common` や `keyboard-configuration` のように、基準では重要でも直感とずれるものがあります。
- **併用の評価:** 併用はテスト後に計算したもので、事前に決めた比較ではありません。

## 再現手順

`ml/build_own_dataset.py` の冒頭の手順で `ml/data/own` を作り、次を実行します。同じ入力から同じデータができることは確認済みです。

```bash
cargo run --release --bin trustauto-train -- --dataset ml/data/own/train.tsv --eval-only --test ml/data/own/test.tsv --test ml/probe_envelope.tsv --test ml/probe_fresh.tsv
```
