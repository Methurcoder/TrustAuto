# ML 実験 3: 実機で壊して得た正解と、機械の事実を使った学習

**結論: 危険な操作の自動許可 1% 未満は、達成も証明もできませんでした。モデルは組み込みません。**

`apt remove` では、ML は危険を見逃さない閾値にすると何も自動許可できません。依存関係とファイルを調べるだけのルールのほうが実用的でしたが、こちらにも実際の穴があります。

## 方法

使い捨ての VM クローン（`TrustAuto-Lab`、Ubuntu 26.04）で、`systemd-nspawn` のコンテナを 1 ケースごとに作り、コマンドを実行してから次の 12 項目を確かめました。

起動、multi-user、SSH ログイン、sudo、apt、dpkg、シェル、D-Bus、ジャーナル、ブート関連ファイル、ネットワーク設定ツール、LVM ツール

| 対象 | ケース数 |
|---|---|
| インストール済みの全パッケージの `apt remove` | 762 |
| 264 ユニットの `systemctl stop` と `restart` | 528 |
| 別の構成（Web、DB、Docker など）で追加したパッケージとユニット | 147 |

- 壊れたと出たケースは、1 件ずつ再実行して確認しました。
- 分割はソースパッケージまたはユニット系統の単位です。
- ML の閾値は、そのグループを学習に使っていないモデルのスコアから決めました。

## 実験中に見つけた問題

| 問題 | 影響 | 対応 |
|---|---|---|
| 並列実行でコンテナ名が衝突した | `apt remove` の 305 件が実行されないまま「壊れない」と記録された。`bash` や `systemd` も含む | 名前を修正して再実行 |
| コンテナにネットワークがない | 代替パッケージを取得できず 35 件が失敗した | 事前にキャッシュして再実行 |
| 負荷による一時的な失敗 | 11 件を誤って「壊れた」と記録した（主に `apt` の確認） | 1 件ずつの再実行で除外 |
| 集計コードで行の名前を判定に使った | ルールの行に ML の結果が出た | 修正。開発データの集計だけに影響 |

## 正解データ

最初の 1,290 ケースのうち、確認後に実際に壊れたのは **62 件（39 グループ）** でした。

- 私が前回「危険」と決めた問題の前提には、誤りがありました。`systemctl stop ssh` は SSH を切りません（ソケット起動のため）。一方で、`libcbor0.10` や `login.defs` の削除は依存関係を通じて SSH を壊します。
- 判定不能が 27 件あります。多くは、コンテナ内で `grub-probe` が失敗して削除が途中で止まったものです。
- 232 件は起動経路（カーネル、initramfs、ブートローダーなど）に関わります。コンテナでは確かめられないので、結果が無事でも安全の証拠にはしません。

## 結果

「ルール」は、削除で失われるパッケージの中に、確認項目を担うファイルか起動経路のファイルがあれば承認要求とするものです。サービスは、動作中かつ有効で、停止が禁止されておらず、既定の依存関係を持つものだけを許可します。ML は取りこぼしゼロになる閾値で評価しました。

分割テスト（開発データとは別のグループ）:

| 方式 | 種類 | 危険の自動許可 | 無害の自動許可 |
|---|---|---|---|
| ML 単体 | remove | 0/14 | **0/138** |
| ML 単体 | stop/restart | 0/1 | 43/85 |
| ルール（ML なし） | remove | 4/14（4 件とも判定不能） | 88/138 |
| ルール（ML なし） | stop/restart | 0/1 | 8/85 |
| ルール + ML | remove | 0/14 | 0/138 |
| ルール + ML | stop/restart | 0/1 | 3/85 |

全 1,290 ケースでのルールの結果:

- 実際に壊れた 62 件の自動許可: 0 件
- 判定不能 27 件の自動許可: 12 件
- 無害の自動許可: remove 490/685、stop/restart 30/518

別構成の 147 件では、壊れたケースは 0 件、判定不能が 1 件でした。ただし、これは安全の証拠になりません（次節の 4 番目）。

remove の分割テストの AUC は 1.0 で、順位付けは正しくできています。それでも閾値を下げざるを得ないのは、`remove bash`（スコア 0.003）のように学習データに同種がない破壊があるからです。

## 数字の限界

1. **目標の 1% 未満を統計的に示せません。** 見逃しゼロで 1% 未満と言うには、独立した危険ケースが約 300 件必要です。この機械で得られたのは全体でも 62 件（39 グループ）で、テストには 9 件（判定不能を含めて 16 件）しかありません。remove のテストで見逃しがゼロでも、14 件では 95% 上限が 19.3% です。
2. **ルールの好成績は循環しています。** ルールが調べるファイルは確認項目から決めているので、確認項目で見つかる破壊を防げるのはほぼ当然です。確認項目にない破壊については何も言えません。
3. **テストは完全には未見ではありません。** 分割の前に、壊れたケースの一覧を見てから特徴量を調整しました。D-Bus の判定は開発データでの見逃しを見て 1 回修正しています。
4. **役割の破壊を測っていません。** 別構成で壊れたケースがないのは、確認項目が OS の機能だけを見ているからです。DB サーバーで `stop postgresql` を実行しても「無害」と記録されます。
5. **起動を実際に確かめていません。** カーネルとブートローダーの影響は、実機の再起動でしか分かりません。
6. **ルールに実際の穴があります。** `remove sudo` が自動許可されます。Ubuntu 26.04 の `/usr/bin/sudo` はパッケージのファイル一覧にないためです。今回は `sudo` パッケージ自身の削除前スクリプトが止めたので壊れませんでした。
7. **`apt remove` の結果は実際より厳しめです。** 実験では `--allow-remove-essential` を付けました。実際の `apt remove bash` は apt が止めます。

## 再現手順

スクリプトは `ml/truth/` にあり、データは `ml/data/truth/` にあります（Git の管理外）。

```bash
python3 ml/truth/train_facts.py ml/data/truth --test --fresh
```

データの収集は、使い捨ての Linux VM で root として実行します。

```bash
sudo TRUSTAUTO_TRUTH_DISPOSABLE=yes python3 ml/truth/truth_lab.py batch CASES OUT --workers 3
```
