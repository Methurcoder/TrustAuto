# TrustAuto 設計

## 結論：実現できるか

実現できます。ただし、仕様の「`sudo` の入力を不要にする」には、設計では消せない代償があります。

**自動昇格の範囲は、そのユーザーとして動く全プログラムにも開放されます。** パスワードなしで昇格できるということは、人間とマルウェアを区別する材料がないということです。npm の postinstall スクリプトでも同じルールを使えます。これは `NOPASSWD` の sudo と同じ性質です。

そのため `allow` と `envelope` には、「このユーザー権限のマルウェアに実行されても許容できる操作」だけを入れてください。`require_tty` は多くのバックグラウンド実行を止めますが、疑似端末を用意されると防げません。

## 脅威モデル

| 対象 | 扱い |
|---|---|
| `trustauto` グループのユーザーと、その権限で動くプログラム | **信頼しない**。argv、環境変数、fd、rlimit、シグナル状態、カレントディレクトリをすべて敵対的な入力として扱う |
| グループ外のユーザー | ブローカーを実行できない（`4750 root:trustauto`） |
| root、`/etc/trustauto`、ビルド成果物 | 信頼する |
| ML モデルの判定 | **誤る前提で設計する**。回避入力を作られる前提でもある |

## 構成

```
シェル関数 ─→ trustauto（権限なし）─┬─→ user 判定: ユーザー権限でそのまま exec
                                   └─→ trustauto-broker（setuid root）
                                         ├ 判定をやり直す（フロントエンドを信用しない）
                                         ├ 監査ログを書く（失敗したら昇格しない）
                                         ├ 必要なら PAM で承認を取る
                                         └ execve で置き換わる（何も残らない）
```

setuid で動くコードを小さくするため、バイナリを分けています。ブローカーのコマンドは `run` と `history` の 2 つだけで、`--policy` のように呼び出し側が設定を差し替える手段はありません。

シェル連携はコマンド行を書き換えず、ポリシーに載っているコマンド名（`ml` モードでは、加えてモデルが学習した管理用プログラム）の関数を定義します。シェルが展開し終えた正確な argv を受け取るので、シェルとの解釈のずれが起きません。パイプやリダイレクトもそのまま動きます。対話シェルにしか作用しないので、既存のスクリプトの動作は変わりません。

## ML を権限の根拠にしない仕組み

判定は `src/engine.rs` の順序で決まります。

1. ルールを照合し、最も厳しいものを採用する。`deny` と `ask` はどのモードでも優先する
2. `rule` と `hybrid` では、ML は `allow` と `envelope` に一致した要求にだけ適用する
3. `ml`（プレビュー）だけは例外で、root が必要なコマンドを ML だけで昇格させうる。管理者が `sudo trustauto mode ml` で明示的に選んだときだけ有効になる
4. ガード（`hard_guard`、`ml` では `ml_alone_guard`）、TTY 要件、外部通信の確認は、Allow を Ask に変えることしかできない

| 誤判定の種類 | `rule` / `hybrid` | `ml` |
|---|---|---|
| 危険なコマンドを安全と判定（範囲外） | どのルールにも合わないので承認要求 | **昇格する**。シェル、インタープリター、カーネルやディスクの操作、秘密のファイル、学習にないプログラム（既定）は除く |
| 危険なコマンドを安全と判定（範囲内） | 昇格する。ただし型付き引数の範囲を超えられない | 昇格する |
| 安全なコマンドを危険と判定 | 承認要求になるだけ | 承認要求になるだけ |
| モデルの破損、NaN、機械の事実の欠損や 8 日超の古さ | 承認要求 | 承認要求 |

「全コマンドを安全と判定するモデル」でも、`hybrid` が範囲を超えないこと、`ml` がシェルなどを昇格させないことを `tests/engine.rs` で検証しています。

`ml` で範囲外の誤判定が起きることは、このモードの性質です。モデルは合格基準に届いておらず、開発用の 4 台では未見の機械で危険グループの 8/217 を見逃しました（[実験 5](ML_EXPERIMENT_5.md)）。`ml` は試験的な機械でだけ使ってください。

### 機械の事実

モデルは、コマンドの引数と機械の事実（dpkg のパッケージと依存関係、systemd ユニット、プロセスのメモリマップ、`ss -p`、PAM の設定、ライブラリやスクリプトの参照）から特徴量を作ります。特徴量の計算は学習コード（`ml/truth/experiment_5/round4_evaluation/reproduction/source`）を `src/facts.rs` に移植したもので、`tests/facts_parity.rs` が 4 台・1,534 行で値の一致を確かめます。

| 項目 | 扱い |
|---|---|
| 収集 | `trustauto-facts`（root、読むだけ）。インストール時、毎日のタイマー、dpkg の実行後 |
| 保存 | `/var/lib/trustauto/facts.json`、`root:trustauto`、`0640`。プロセスの一覧を含むので、グループ外には見せない |
| ブローカー | root 所有で、ディレクトリをたどって root 以外が書けないことを確かめてから読む。満たさなければ ML は使わない |
| フロントエンド | 読めれば読むが、結果はどの経路を通るかの選択にしか使わない |
| 古さ | 8 日を超えたら使わない（承認要求） |
| 対象の権限 | 学習時の「対象」は操作ごとに決め方が違った。実行時は最初の絶対パス、作成系（`touch`、`mkdir`、`tee`）で存在しなければその親ディレクトリの権限を使う。`ln -sf` のように学習時と違う対象を選ぶ場合がある |

### ML のみモードで root が必要かの判断

すべてのコマンドを root で実行すると、自分のファイルが root の所有になるなどの害があります。`ml` では、次のどれかに当たるときだけ ML に判断させ、それ以外は普段の権限で実行します。

- プログラムが sbin にある
- 変更を目的とする操作（学習コードの `ALWAYS_CHANGES` などの一覧）で、パスの引数がない
- パスの引数を本人の権限で読めない、または変更を目的とする操作で書けない

この判断はヒューリスティックです。外れても、ML の判断を経ずに昇格することはありません。

シェル連携は、`ml` ではルールのコマンド名に加えて、モデルが学習したプログラムのうち管理用のもの（sbin にあるか、変更を目的とするもの）を関数で包みます。

### 外部との通信

`network.ask`（既定でオン）は、外部と通信しうるコマンドの Allow を Ask に変えます。プログラム名（`curl`、`ssh` など）、サブコマンド（`apt update`、`git pull` など）、引数（`://`、`user@host:`、`--keyserver` など）で判断します。一覧に頼るので、漏れはありえます。

## ルールが安全である理由

拒否リストは完全にできません。`apt-get -o APT::Update::Pre-Invoke::=/bin/sh update`、`systemctl status` のページャーからの `!sh`、`find -exec`、`tar --checkpoint-action` のように、普通のコマンドから root シェルに抜ける方法は多数あります。

そこで、既定で拒否し、型付きの引数だけを許可します。

- `{pkg}`、`{unit}`、`{word}`、`{int}` は `-` で始まる値に一致しないので、オプションを注入できません
- `{pkg}` は `/`（ローカルファイル）、`=`（バージョン指定）、`.`（apt が正規表現として解釈）、末尾の `-`（削除の意味）を拒否します
- `{path:...}` はシンボリックリンクを解決した後のパスも確認します
- `{any}` を `allow` と `envelope` で使うと、ポリシー全体が読み込みエラーになります
- シェルやインタプリタなど、任意コード実行に等しいプログラムへの `allow` と `envelope` も読み込みエラーになります

`src/analyze.rs` のリストは多層防御の一部で、セキュリティ境界ではありません。

## ブローカーの防御

| 攻撃 | 対策 |
|---|---|
| `LD_PRELOAD`、`PATH` などの環境変数 | 環境を消去し、固定値と検証済みの `TERM`、`LANG` だけで作り直す |
| ページャーやエディタからのシェル脱出 | `PAGER=cat`、`SYSTEMD_PAGERSECURE=1`、`EDITOR=/bin/false` などを設定する |
| 判定と監査の間にシグナルで止める | 最初に実 UID も 0 にして、呼び出し元からシグナルを送れないようにする |
| 小さい `RLIMIT_FSIZE` で監査ログを切り詰める | rlimit をすべて再設定する |
| 継承した fd を root プロセスに渡す | fd 3 以降を閉じる（`execve` の直前にも再度閉じる） |
| 偽のバイナリを実行させる | 固定の安全な検索パスだけを使い、ファイルと親ディレクトリすべてが root 所有であることを確認する |
| シンボリックリンクで別名を使う | 実体と名前が異なる場合は拒否する（`reboot` → `systemctl` のように argv[0] で動作が変わるため） |
| ポリシーや監査ログの改ざん | 所有者とパーミッションを確認し、問題があれば昇格しない。監査ログは `O_NOFOLLOW` で開く |
| 引数で監査ログや承認画面を偽装する | ログは JSON エスケープし、画面表示は制御文字と Unicode の不可視文字をエスケープする |
| stdin をすり替えてパスワードを渡す | `/dev/tty` からのみ読む。空パスワードのアカウントは承認者になれない |

パスワード入力で Ctrl-D（端末の EOF）を押すと、その場で「approval cancelled」として拒否する。2026-11-06 までは認証失敗の 1 回として数え、最大回数まで聞き直していた。拒否が早まるだけで、許可の条件は変わらない。

## 既知の制限

| 制限 | 影響 |
|---|---|
| 終了コードを記録しない | `execve` で置き換わるため、履歴は「開始の記録」まで。記録するには親プロセスを残す設計変更が必要 |
| TIOCSTI | root のコマンドが終わった後に、ユーザー権限のプログラムが端末へ入力を注入できる古典的な問題。Linux 6.2 以降の `dev.tty.legacy_tiocsti=0` で防げる。sudo の `use_pty` に相当する仕組みはない |
| パスワードの入力を盗まれる | 疑似端末を操るプログラムの下で承認すると読まれる。sudo と同じ |
| 監査ログの容量 | 拒否される要求でも 1 行書くので、グループのメンバーはディスクを埋められる。埋まると昇格が止まる（安全側） |
| カレントディレクトリ | 常に `/` で実行するので、相対パスの引数は動かない |
| 別名コマンド | `reboot` のようなコマンドは拒否される。`systemctl reboot` と書く必要がある |
| PAM 設定 | `config/pam.d-trustauto` は Debian/Ubuntu 向け |
| コンテキスト信号 | SSH 接続の判定などは呼び出し元が消せる環境変数に依存する。リスクを上げる方向にしか使わない |
| 承認者が別端末にいる場合 | 未対応。承認は要求元の端末で行う（キュー型の承認は将来の課題） |
| ML の精度 | 合格基準に未達。`ml` モードは範囲外の危険な操作を昇格させうる |
| 事実の読み込み時間 | ML を使う判定ごとに約 20 ms（macOS での測定）。Linux では未測定 |
| 事実の鮮度 | 毎日とパッケージ変更後に更新するが、その間の変化（新しいサービスの起動など）は反映されない |
